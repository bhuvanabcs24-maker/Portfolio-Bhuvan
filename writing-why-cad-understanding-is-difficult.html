1. The Deceptive Simplicity of CAD Files

When I began building ForgeIQ, the initial product vision sounded straightforward: a mechanical buyer uploads a 2D DXF blueprint or 3D CAD drawing, the system extracts the geometry, and quotes the cutting cycle time and raw material cost automatically.

In software engineering, we often assume structured file formats follow clean specifications. A JSON API returns typed objects, an SVG contains vector paths, and a database table enforces schemas. CAD files do not work this way.

In practice, Computer-Aided Design (CAD) files are closer to an unorganized bucket of geometric drawing instructions created by different drafting software suites (AutoCAD, SolidWorks, Fusion 360), exported through varying translators, and drawn by human draftsmen who care about how a drawing looks on paper rather than how a parser interprets its data structures.

2. The DXF Format: Group Codes, Entities & Micro-Gaps

The Drawing Exchange Format (DXF), created by Autodesk in 1982, represents drawings using tagged data pairs called group codes. A line is represented not as an atomic vector primitive, but as a sequence of integer keys and coordinates:

LINE Entity in ASCII DXF: 0 (Entity Type) LINE 8 (Layer Name) CONTOUR 10 (Start Point X) 120.500 20 (Start Point Y) 45.250 11 (End Point X) 185.000 21 (End Point Y) 45.250

The fundamental architectural challenge is that a 2D DXF file contains no inherent hierarchy of parts or closed polygons. It simply stores thousands of independent, unlinked entities: LINE, ARC, CIRCLE, LWPOLYLINE, and SPLINE.

Worse, human draftsmen frequently produce micro-gaps. When a designer visually snaps two lines together on a 4K monitor, their endpoints might be separated by 0.004 mm. To a human machinist viewing a printed blueprint, the contour appears closed. To a computational polygon area algorithm (like Green's theorem or Shoelace), the path is open, causing the algorithm to either drop the polygon entirely or produce infinite loops.

3. Why Vision Models and LLMs Fail on CAD

A natural question I explored during early prototyping was: Can we rasterize the DXF drawing into an image and pass it to a multimodal vision model (such as Gemini 2.5 Flash or GPT-4o)?

I tested this approach against benchmark industrial brackets. The results failed our operational accuracy criteria:

  • Scale Blindness: A vision model cannot differentiate between a 50 mm bracket and a 500 mm bracket if both drawings are scaled to fit a standard 1024x1024 image frame, unless it perfectly reads every dimensional witness line.
  • Hallucinated Geometry: When prompted to calculate cutting lengths or sheet metal scrap area, vision LLMs produced variance between 20% and 50% across identical prompts.
  • Zero Floating-Point Rigor: In laser cutting, the difference between a 10.0 mm hole and a 10.2 mm hole determines whether an M10 dowel pin fits or binds. Multimodal models predict tokens based on statistical likelihood; they do not calculate Euclidean distances.

This experiment proved an essential architectural rule: probabilistic models must never be placed on the critical path of physical geometry parsing.

4. The Graph-Based Vertex Snapping Algorithm

To solve the problem of disconnected entities and micro-gaps, I implemented a graph-based preprocessor in Python using ezdxf and networkx.

RAW DXF ENTITIES SPATIAL ADJACENCY GRAPH CLOSED CYCLES [Line 1: (0,0) -> (10,0)] ──> [Node (0,0)] <── snapped ──> [Outer Boundary] [Line 2: (10.003,0) -> (10,10)] (0.01mm tolerance threshold) [Hole 1 (Circle)] [Line 3: (10,10) -> (0,10)] [Hole 2 (Slot)] [Line 4: (0,10) -> (0,0)]

Instead of assuming entities are ordered sequentially, the algorithm executes four stages:

  1. Entity Ingestion: Extract all LINE, ARC, and LWPOLYLINE segments into discrete line segments.
  2. Spatial Clumping (KD-Tree): Query all endpoints against a KD-Tree with a 0.01 mm tolerance threshold. Any two vertices within 0.01 mm are snapped to an identical centroid coordinate.
  3. Graph Adjacency Construction: Insert edges into an undirected graph where nodes are unique snapped vertices.
  4. Cycle Basis Extraction: Use cycle-finding algorithms to detect closed loops. The largest loop by bounding box represents the outer sheet boundary; all interior closed loops represent hole piercings.
Python (Backend Implementation) Extracting closed loops via spatial snapping 
import ezdxf
from scipy.spatial import KDTree
import networkx as nx

def build_snapped_geometry_graph(msp, tolerance_mm=0.01):
    raw_edges = []
    points = []
    
    for entity in msp.query("LINE ARC LWPOLYLINE"):
        for segment in extract_segments(entity):
            p1, p2 = segment.start, segment.end
            points.extend([p1, p2])
            raw_edges.append((p1, p2))
            
    # Spatial KD-Tree snapping
    tree = KDTree(points)
    snapped_map = {}
    for pt in points:
        idx = tree.query_ball_point(pt, r=tolerance_mm)
        # Canonical centroid for all points within tolerance
        snapped_map[pt] = tuple(points[idx[0]])
        
    # Construct adjacency graph
    G = nx.Graph()
    for p1, p2 in raw_edges:
        u, v = snapped_map[p1], snapped_map[p2]
        if u != v:
            dist = ((u[0]-v[0])**2 + (u[1]-v[1])**2)**0.5
            G.add_edge(u, v, weight=dist)
            
    # Extract closed cycles
    cycles = nx.cycle_basis(G)
    return cycles

5. Calculating Sheet Metal Scrap & Pierce Counts

Once clean closed polygons are reconstructed, manufacturing parameters become mathematically exact:

  • Laser Pierce Count: Equal to the number of interior closed cycles plus one (for the outer contour). Each pierce adds a fixed dwell time (e.g. 0.8 seconds) and consumable gas cost.
  • Cutting Perimeter: The exact Euclidean sum of all edges in the cycle basis, directly determining the machine feed-rate duration.
  • Raw Sheet Scrap: Bounding box area minus the sum of interior polygon areas, giving factory estimators the true material utilization ratio.

In our benchmark test suite across 50 production drawings, this deterministic pipeline achieved 96.9% quotation accuracy against manually validated machine-shop estimates.

6. 3D STEP Models: B-Rep & Mesh Tessellation

For 3D CNC milling and turning, 2D vector parsing is insufficient. Customers upload STEP (Standard for the Exchange of Product model data) or STL mesh files.

STEP files utilize Boundary Representation (B-Rep), defining 3D solid topology through faces, edges, and vertices connected by mathematical NURBS surfaces. Parsing B-Rep solids requires heavy geometric kernels (such as Open CASCADE).

When evaluating system performance under concurrent load, I discovered that parsing a 50MB 3D model takes between 300 ms and 1200 ms of continuous CPU calculation. Because Python's AsyncIO event loop is single-threaded, running this calculation inside an async def handler froze the server, blocking all incoming HTTP requests.

To maintain sub-20ms API response times for concurrent users, I offloaded 3D mesh tessellation to a ProcessPoolExecutor pool, cleanly isolating CPU-bound floating-point arithmetic from the ASGI network event loop.

7. The Engineering Boundary: Deterministic vs Probabilistic

Where does Artificial Intelligence belong in this architecture?

In ForgeIQ, I instituted a strict boundary between deterministic code and generative AI:

  • Deterministic Layer (Python / ezdxf / ProcessPool): 100% responsible for physical dimensions, cutting perimeters, pierce counts, hole diameters, surface area, and bounding volumes.
  • Probabilistic AI Layer (Google Gemini 2.5 Flash): 100% responsible for interpreting unstructured human context: parsing buyer RFQ notes, detecting ambiguous tolerance callouts, identifying alloy specifications from drawing title blocks, and recommending appropriate machining classes.

The verified scalar metrics from the deterministic parser are injected into the LLM's system prompt as immutable ground truth. The model is explicitly forbidden from recalculating dimensions, and its response is constrained by strict Pydantic schemas.

8. Lessons from Building ForgeIQ

Building the CAD ingestion engine in ForgeIQ provided several lasting software engineering takeaways:

  1. Never Trust Raw User Input: Real-world CAD files will violate standard specifications. Tolerances and defensive spatial graph snapping are mandatory.
  2. Respect the Computational Nature of the Task: Use mathematical graph algorithms for geometry, relational databases for financial transactions, and language models for semantic comprehension. Do not force an LLM to do arithmetic.
  3. Hermetic Test Fixtures are Worth the Investment: Creating an offline MockAIProvider and caching parsed CAD fixtures allowed my 47-test suite to run in seconds on every commit without external API dependencies.
