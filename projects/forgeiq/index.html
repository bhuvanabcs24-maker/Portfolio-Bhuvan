01 · Domain Context

The Workflow Problem

Manufacturing procurement involves multi-step operational coordination across disjointed stakeholders:

• Product Requirements
Unstructured buyer specs & alloy grades
• Technical Drawings
2D DXF vector geometry & hole patterns
• RFQ Generation
Standardizing parameters for bidding
• Supplier Discovery
Matching machine bed sizes & capabilities
• Quotation Comparison
Evaluating material, piercing, and finishing costs
• Production Planning & Tracking
Shop-floor stages from laser cut to dispatch

These workflows traditionally involve significant manual coordination: estimators manually opening vector files, calculating cut paths with calipers or standalone desktop tools, cross-referencing metal sheet prices in spreadsheets, generating quotes via email, and maintaining disconnected status logs. ForgeIQ was engineered to address this fragmented pipeline as a software engineering problem.

02 · Engineering Complexity

Why the Problem is Difficult

1. Physical Tolerances vs. AI Hallucination

Vision LLMs are probabilistic. They hallucinate coordinate positions, confuse hole diameters, and drop millimeter scale factors. In CNC machining, a 0.5mm variance ruins part assembly and wastes expensive raw alloy stock.

2. Unstructured Multi-Modal Inputs

CAD drawings contain complex nested entities (polylines, splines, circle loops, text blocks) while buyer notes arrive as ambiguous natural language instructions with differing alloy nomenclatures.

3. Stateful Multi-Stage Shop-Floor Tracking

An order is not a simple boolean state. It traverses 9 distinct manufacturing phases with inventory reservations, quality check rejections, and strict role permissions between buyers and machine operators.

4. CPU-Bound Vector Parsing & Concurrency

Parsing thousands of vector vertices synchronously blocks Python's asynchronous event loop, degrading API response times under high-concurrency quotation requests.

Core Capabilities · Deep Dive

Key Technical Features

An architectural breakdown of the operational mechanisms driving order intake, algorithmic pricing, finite-state tracking, multi-agent orchestration, and marketplace discovery.

AI Order Intake

Implemented

Document & Drawing Understanding + Requirement Extraction: Traditional manufacturing intake relies on engineers manually opening technical PDFs, reading drawing title blocks, and inspecting 2D CAD files to decipher specifications. ForgeIQ automates this ingestion via a two-tier extraction pipeline:

Deterministic Geometry Extraction (ezdxf)

Parses 2D DXF vector drawings mathematically. Traverses LWPOLYLINE, LINE, and CIRCLE entities to compute exact outer perimeter cut length, inner piercing counts, total bounding box dimensions (X, Y), and true sheet area without probabilistic error.

Unstructured Specification Parsing (LLM + Pydantic)

Translates natural language buyer RFQ notes and PDF drawing title blocks into strict Pydantic schemas. Extracts alloy codes (e.g., SS304, AL6061-T6), plate thicknesses (e.g., 3.0 mm), surface treatments (powder coated, anodized), and tolerance grades (ISO 2768-m).

AI Quotation Engine

Implemented · 96.9% Benchmark Accuracy

Parametric Pricing Workflow: Converts extracted physical geometries and material requirements into deterministic, instant manufacturing quotes. Rather than guessing prices via unstructured text generation, ForgeIQ uses an algorithmic cost model grounded in physical shop-floor mechanics:

Total Price = (Material Mass × Raw Cost/kg) + (Cut Length ÷ Feed Rate × Laser Cost/min)
             + (Pierce Count × Pierce Dwell Cost) + Bending Operations + Setup/Handling + Target Margin

Accounts for bounding-box nesting efficiency against standard stock sheet sizes (e.g., 2500 × 1250 mm) to capture scrap factor. Achieved 96.9% quotation accuracy when evaluated against verified production machine-shop benchmark bids.

Production Workflow

Implemented · 9 Discrete Stages

Configurable Manufacturing Workflow Stages: Real manufacturing operations require rigorous, auditable stage transitions. ForgeIQ models the entire manufacturing lifecycle as an auditable finite state machine spanning 9 discrete stages:

1. RFQ Submitted 2. Quoted 3. Order Confirmed 4. Material Allocated 5. CNC Laser Cut / Machined 6. Bending / Secondary Ops 7. Quality Inspection 8. Dispatched 9. Delivered

Shop-Floor Configurability: Machine shops can configure and bypass non-applicable operations (e.g., flat laser jobs bypass Stage 6 Bending). Every stage transition is recorded in an immutable PostgreSQL audit ledger (order_stage_transitions) capturing user ID, timestamp, QA inspector sign-off, and dimensional tolerance notes.

05 · Applied AI Engineering

AI Architecture & Grounding

The AI subsystem is engineered around the principle of strict boundary separation:

Pluggable Provider Factory

Implemented an abstract BaseAIProvider class with concrete implementations for MockProvider, GeminiProvider, and OpenAIProvider. Decouples application logic from specific vendor SDKs and enables automated offline testing in CI without token costs.

Structured Schema Guardrails

LLM outputs are strictly bound to Pydantic models with type constraints on alloy codes, thickness ranges, and tolerance thresholds. Eliminates markdown formatting errors and guarantees parseable JSON responses.

Domain Grounding Prompting

Prompts incorporate mathematical bounds pre-calculated by the CAD parser. The LLM is prohibited from generating geometry numbers; its role is strictly translating unstructured buyer notes into standard manufacturing tags.

06 · Backend Engineering

Backend Architecture (FastAPI & Python)

Built as a high-performance modular monolith with 40+ REST endpoints conforming to OpenAPI 3.1:

Tenant Isolation & RBAC

JWT claims enforce role-based access control distinguishing between buyer and manufacturer_admin roles. Queries automatically scope database access by tenant_id to prevent cross-tenant data leakage.

CPU-Bound Process Offloading

Python's Global Interpreter Lock (GIL) and single-threaded async event loop are protected from geometry calculation overhead. Intensive DXF contour iterations run in a dedicated ProcessPoolExecutor.

Sliding-Window Rate Limiting

Implemented sliding-window rate limiters across public quote submission endpoints to protect downstream database resources and AI provider quotas from request flooding.

07 · Data & Vector Storage

Database & Retrieval Architecture

PostgreSQL hosted on Neon / Supabase serves as both the relational ledger and high-dimensional vector store:

pgvector Similarity Matching

Manufacturer capabilities and machine specs are embedded into 1536-dimensional vector representations. Cosine distance queries (<=>) match new RFQs to optimal factories based on equipment bed sizes and alloy expertise.

Hybrid Semantic & Keyword Search

Combines PostgreSQL full-text search (tsvector/tsquery) for exact alloy grade matches (e.g., AISI-316L) with vector similarity for descriptive manufacturing constraints.

Relational State Machine

The 9 production stages are modeled as immutable historical rows in an order_stage_transitions table, providing an audit trail of every status transition with user ID, timestamp, and notes.

Architectural Trade-Off Analysis

Technical Decision Cards

Rigorous engineering decisions evaluated against problem context, architectural choices, technical justification, and accepted trade-offs:

Why PostgreSQL? Database
Problem:
ForgeIQ needs relational data for customers, orders, quotations, production workflows, and permissions.
Decision:
PostgreSQL (hosted on Neon Cloud & Supabase).
Reason:
Strong relational modeling, transactional guarantees, mature indexing, and native compatibility with pgvector for unified storage.
Trade-off:
More structured schema management compared with document-oriented storage.
Why FastAPI? Backend API
Problem:
Need high-throughput REST API layer to handle concurrent RFQ submissions, multi-part CAD uploads, and strict data validation across 40+ endpoints.
Decision:
FastAPI with Python async ASGI server.
Reason:
Native async/await event loop, automated OpenAPI 3.1 schema generation, robust Pydantic v2 validation, and direct access to Python's CAD geometry ecosystem (ezdxf).
Trade-off:
CPU-bound tasks (intense DXF vector math) block the single-threaded event loop unless dispatched to a secondary ProcessPoolExecutor.
Why Next.js? Frontend
Problem:
Need an interactive, performant web interface serving both prospective buyers and factory operators with modern layouts and reliable state management.
Decision:
Next.js App Router with TypeScript and Tailwind CSS.
Reason:
Server-side rendering for fast initial loads, robust App Router layout architecture, strict TypeScript typing for API contracts, and rapid UI development.
Trade-off:
React hydration bundle overhead and complex server/client component boundaries compared to zero-JS static HTML.
Why pgvector? Vector Storage
Problem:
Manufacturer capability matching requires high-dimensional semantic similarity search over equipment specs and job constraints.
Decision:
pgvector extension inside PostgreSQL.
Reason:
Keeps relational data (orders, users, factories) and vector embeddings inside a single ACID transactional boundary—eliminating dual-write inconsistency, external network latency, and synchronization pipelines.
Trade-off:
Slightly higher resource footprint on PostgreSQL memory than specialized in-memory vector indices (e.g., Pinecone) at massive billion-vector scale.
Why Provider Abstraction? AI Architecture
Problem:
Direct coupling to a single proprietary LLM API causes vendor lock-in, unreliability during provider outages, and high API token costs during automated CI testing.
Decision:
Pluggable BaseAIProvider interface with Mock, Gemini, and OpenAI adapters.
Reason:
Allows unit and E2E tests to run deterministically and offline with zero API cost using MockAIProvider, while allowing production deployments to switch between Gemini and OpenAI via environment variables.
Trade-off:
Requires maintaining a unified internal interface and serialization wrapper across disparate provider SDK schemas.
Why Playwright? Testing
Problem:
Multi-step manufacturing workflows (multi-file DXF upload, instant quote rendering, multi-role portal state updates) require reliable end-to-end browser verification without flaky test runs.
Decision:
Playwright for end-to-end automated testing.
Reason:
Built-in auto-waiting eliminates race conditions in asynchronous client-server interactions; native multi-context isolation enables testing buyer and manufacturer roles concurrently.
Trade-off:
Heavier test execution overhead and longer CI runtimes compared to pure in-memory headless unit tests.

10 · Debugging & Resolution

Engineering Challenges Encountered

Challenge 1: Malformed CAD Splines & Unclosed Polylines
Problem: Real-world CAD files frequently contain disconnected polyline segments, duplicate vertices, and unclosed boundary loops that crashed naive polygon area algorithms.
Resolution: Implemented a graph-based vertex snapping algorithm with a 0.01mm tolerance threshold. Traverses connected edges to reconstruct clean closed loops before computing raw sheet utilization.
Challenge 2: Database Connection Saturation Under Load (N+1 Issue)
Problem: Initial load tests crashed at 860 req/sec due to connection pool starvation caused by 12 independent SQL queries per order status check.
Resolution: Rewrote nested queries into unified Common Table Expressions (CTEs) with composite B-Tree indexes on (tenant_id, order_id, stage_timestamp), dropping database roundtrips to a single query.
Challenge 3: Third-Party AI Rate Limits in Production Testing
Problem: Running automated Playwright suites against live cloud AI providers led to frequent 429 Rate Limit errors and slow test runs.
Resolution: Implemented the Mock AI Provider pattern in test environments. Tests execute in seconds with zero external network flakiness, while production switches seamlessly to Gemini.
11 · Engineering Growth

What I Learned

1. Deterministic Foundations are Non-Negotiable in Physical Systems

AI should enhance workflows, not serve as a substitute for rigorous domain mathematics. Building ForgeIQ proved that isolating probabilistic models to natural language tasks while keeping geometry calculation deterministic is the only credible architecture for manufacturing software.

2. Profile First, Optimize Second

Before profiling with load generators, I assumed CAD parsing was the primary bottleneck. Load testing revealed that 80% of request latency was actually database roundtrip contention (N+1 queries). Measuring with empirical tools prevented wasted optimization efforts.

3. Automated Testing Enables Fearless Refactoring

Having 33 Pytest unit tests and 14 Playwright E2E tests allowed me to rewrite database query layers and introduce multi-process geometry execution without breaking quotation calculation or order stage progression.
